KnotEmployee

A multi-tenant iOS employee scheduling app for small businesses — handling the full workforce management loop from scheduling and time tracking to shift swaps, time off, and team messaging.

Unique Value: Paper schedules and group texts were the only options. KnotEmployee gives small business owners a purpose-built tool that handles every step of the employee lifecycle in one app.

Problem

Small businesses — bakeries, salons, cafes — manage their staff with paper schedules pinned to the wall and group texts that bury shift changes in noise. There's no record of who clocked in late, no approval trail for time off, no way to pick up an open shift without calling someone. KnotEmployee replaces all of it: a single app where managers build schedules, approve requests, and see labor costs in real time, while staff clock in, swap shifts, and message the team — live, on their phones.

Challenge-Based Learning

Challenge: Build a production-grade, multi-tenant scheduling system where two distinct user roles have entirely different surfaces, while keeping all business data completely isolated between tenants and pushing real-time updates to every connected device.
Approach: Every database table carries tenant_id NOT NULL, the JWT carries tenant claims so reads are row-level-policy enforced, and all inserts reference Config.tenantId — the app is architecturally incapable of leaking one tenant's data to another. Real-time sync uses Supabase Realtime websockets so schedule changes, new messages, and approval updates arrive without polling. Push notifications flow through a Deno Edge Function triggered by a database INSERT, which calls APNs directly — no third-party SDK needed.
Outcome: A TestFlight-ready iOS app with two complete role surfaces, real-time sync, server-side push notifications, a labor cost report with CSV export, and a custom design system — no external UI libraries, no third-party analytics SDK.

Architecture

The app has two entirely separate view hierarchies gated by the authenticated user's role:

  • Manager surface — schedule builder, template library, labor report, approval queues (time off + shift swaps), team directory, broadcast messaging
  • Staff surface — clock in/out with break tracking, weekly schedule, time off requests, shift swap requests, open shift board, direct messaging, earnings estimate

Supporting systems:

  • Config — app-level singleton holding tenantId; every database write reads from here, making cross-tenant writes structurally impossible
  • KnotTheme / BakeryCoTheme — design system with adaptive color pairs, UINavigationBarAppearance configured with adaptive UIColor for full dark mode support
  • Realtime channels — one channel per tenant per data type (schedule, messages, notifications) subscribed on session start and torn down on sign-out
  • BackgroundLock — cream overlay with lock icon applied via scenePhase when the authenticated app leaves the foreground
  • Push notification pipeline — app event → kn_notifications INSERT → Supabase Edge Function → APNs production server → device

Multi-Tenant Architecture — Built In from Day One

Every table in the database has tenant_id NOT NULL. Row-level security policies enforce that a JWT can only read rows where tenant_id matches the claim in the token. On the app side, every INSERT pulls Config.tenantId — there is no code path that can write to the wrong tenant.

MULTI-TENANT INSERT — ShiftService.swift All inserts carry tenant_id from Config — no code path can write to the wrong tenant. 
func createShift(_ shift: Shift) async throws {
    try await supabase
        .from("shifts")
        .insert([
            "tenant_id": Config.tenantId,
            "employee_id": shift.employeeId,
            "start_time": shift.startTime.iso8601String,
            "end_time": shift.endTime.iso8601String,
            "role": shift.role
        ])
        .execute()
}

Row-level security on the Supabase side ensures reads are equally locked down — the JWT tenant claim is checked server-side on every query, so even a malformed request can't read another tenant's rows.

Real-Time Updates via Supabase Realtime

Schedule changes, new messages, and incoming notifications all update live without any polling. The app subscribes to a per-tenant Realtime channel on sign-in and tears it down on sign-out. When a Postgres row changes, the channel fires and the view model reloads only the affected data.

REALTIME SUBSCRIPTION — ScheduleViewModel.swift Per-tenant websocket channel — schedule updates push live to every connected device. 
func subscribeToSchedule() {
    supabase.realtime
        .channel("schedule-\(Config.tenantId)")
        .on(
            .postgresChanges,
            filter: .init(event: .all, schema: "public", table: "shifts")
        ) { [weak self] _ in
            Task { await self?.loadCurrentWeek() }
        }
        .subscribe()
}

Push Notifications — No Third-Party SDK

Push notifications are driven entirely by the database: the app writes an INSERT into kn_notifications, a Deno Edge Function subscribed to that table picks it up, and the function calls the APNs production server directly with the device token. No Firebase, no OneSignal — just the native pipeline.

PUSH NOTIFICATION TRIGGER — NotificationService.swift INSERT into kn_notifications → Edge Function picks up the row → APNs delivery. 
func notify(userId: String, title: String, body: String) async throws {
    try await supabase
        .from("kn_notifications")
        .insert([
            "tenant_id": Config.tenantId,
            "user_id": userId,
            "title": title,
            "body": body,
            "sent": false
        ])
        .execute()
    // Deno Edge Function watches this table and calls APNs
}

The Edge Function approach decouples notification delivery from the iOS app entirely — adding a web dashboard later would send push notifications through the exact same pipeline without any app changes.

Background Lock & Full Dark Mode

When the authenticated app leaves the foreground, a cream overlay with a lock icon covers the screen immediately — no authenticated content is visible in the app switcher. This is handled with a single scenePhase change observer applied at the root view level.

BACKGROUND LOCK — RootView.swift scenePhase observer covers authenticated content whenever the app is not active. 
struct RootView: View {
    @Environment(\.scenePhase) private var scenePhase
    @State private var isLocked = false

    var body: some View {
        ZStack {
            MainTabView()
            if isLocked {
                BackgroundLockOverlay()
            }
        }
        .onChange(of: scenePhase) { _, newPhase in
            isLocked = (newPhase != .active)
        }
    }
}

Dark mode uses a custom KnotTheme with adaptive color pairs defined via Color(UIColor { traits in … }). Navigation bars are updated with UINavigationBarAppearance using adaptive UIColor — so every surface flips correctly without any explicit colorScheme checks in individual views.

ADAPTIVE COLORS — KnotTheme.swift Adaptive Color pairs — every surface flips correctly without per-view colorScheme checks. 
extension Color {
    static let knotSurface = Color(UIColor { traits in
        traits.userInterfaceStyle == .dark
            ? UIColor(hex: "#1C1410")  // deep espresso
            : UIColor(hex: "#FDF8F2")  // warm cream
    })
    static let knotAccent = Color(UIColor { traits in
        traits.userInterfaceStyle == .dark
            ? UIColor(hex: "#E8C87A")  // soft gold
            : UIColor(hex: "#B8960C")  // rich gold
    })
}

Key Decisions

  • Multi-tenant from the start — tenant_id NOT NULL on every table, JWT claims enforced server-side with row-level security, and Config.tenantId on every app-side insert. Adding a second business client requires no schema changes and no code changes.
  • Supabase Realtime over polling — websocket channels eliminate the latency and battery cost of repeat HTTP requests; schedule and message updates are pushed the instant the database row changes.
  • Database-triggered push notifications via a Deno Edge Function — keeps push delivery logic on the server, avoids any third-party SDK dependency, and works identically from a future web dashboard without touching the iOS app.
  • MetricKit only for crash reporting — no third-party analytics or crash SDK installed; crash data flows through Apple's native infrastructure with no external data sharing.
  • Custom KnotTheme design system with a client-specific BakeryCoTheme — warm cream, espresso, rose, and gold with Cormorant Garamond and monospace type. Onboarding, navigation bars, and every view surface adapt automatically through the adaptive color layer.
  • @Observable over ObservableObject — the new Swift observation macro reduces boilerplate and doesn't require @Published on every property; view updates are more granular and the code is easier to read.
  • No external UI libraries — all components are custom SwiftUI. This keeps the bundle small, avoids SDK compatibility issues across iOS versions, and means every pixel matches the KnotTheme spec exactly.

Outcome

KnotEmployee demonstrates a production-quality multi-tenant iOS application: real-time websocket sync, server-driven push notifications through a custom Edge Function pipeline, role-based access across two complete user surfaces, drag-and-drop scheduling with a labor cost report, and a fully custom design system — all with no third-party UI libraries or analytics SDKs. The first client, The Bakery Co., is piloting the app in TestFlight.

What I Learned

  • Designing a multi-tenant data model where tenancy is enforced at both the database layer (RLS) and the app layer (Config.tenantId)
  • Setting up and managing Supabase Realtime websocket channels per tenant with proper subscribe/unsubscribe lifecycle
  • Writing a Deno Edge Function that responds to Postgres INSERTs and calls the APNs production HTTP/2 API directly
  • Building adaptive color systems using Color(UIColor { traits in … }) pairs that cover full dark mode without per-view checks
  • Using @Observable instead of ObservableObject — the newer macro-based observation model and when it's the right choice
  • Implementing a background lock via scenePhase to prevent sensitive data from appearing in the iOS app switcher
  • Designing for two distinct user roles within a single binary — gating entire view hierarchies by role without leaking one surface into the other
